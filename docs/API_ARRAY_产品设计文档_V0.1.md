## 1. 文档目的与冻结规则

本文档定义 API ARRAY 第一阶段的产品边界、用户体验、核心概念、信息架构、运行模型、安全原则、非功能指标和验收标准，是 V0.1 设计与实现的共同基线。

本文档中的内容分为三类：

- **冻结决策**：第一版必须遵守，修改时必须升级文档版本并记录原因。
- **实现建议**：允许在不改变产品行为和用户承诺的前提下调整。
- **待验证假设**：需要通过原型、测试或用户反馈验证，不构成对外承诺。

变更冻结项时，必须至少记录：变更内容、变更原因、受影响模块、兼容性影响、安全影响和迁移方式。

## 2. 产品定义

### 2.1 一句话定位

安装软件，放入你的 API，立即获得一个经过体检、自动容错、可统一调用、可稳定审计并带有完整活文档的本地端点。

### 2.2 产品本质

API ARRAY 对普通用户表现为“本地 API 钱包”，对专业用户表现为“本地优先、可视化编排的多供应商 API 网关与控制平面”。

产品将底层按照小型组织管理 API 基础设施所需的可靠性标准建设，同时把日常使用门槛降低到会填写 API 地址和 API Key 的个人开发者也能立即上手。

### 2.3 用户价值闭环

```text
添加 API
  → 安全保存密钥
  → 自动识别并体检能力
  → 编排路由与策略
  → 发布本地统一端点
  → 复制代码立即运行
  → 持续观察、审计与故障切换
```

产品不以“接入了多少供应商”作为唯一价值，而以“统一后是否能立即理解、立即调用、持续可靠运行”作为核心产品力。

### 2.4 产品原则

1. **本地优先**：密钥、配置、路由和默认审计数据保存在用户设备上。
2. **安装即用**：首版不要求用户部署 Docker、数据库或 Web 后端。
3. **专业内核，低门槛界面**：底层可靠性面向小型组织，默认交互面向个人开发者。
4. **真实能力优先**：区分已验证能力、供应商声明、系统推断和用户声明。
5. **统一之后立即可用**：每个 Publisher 必须同步生成活文档与可运行示例。
6. **配置与实现分离**：Provider YAML 描述供应商差异；Rust Adapter 实现协议能力。
7. **安全默认值**：默认最小暴露、最少记录、密钥不出库、配置导出不带密钥。
8. **运行时独立**：关闭界面不等于停止服务，UI 故障不应中断已发布端点。
9. **可渐进揭示复杂度**：简单视图和专业画布使用同一份运行模型。
10. **可扩展但不提前泛化**：首版聚焦 AI API，同时为未来协议和部署形态保留清晰扩展点。

## 3. 目标用户

### 3.1 核心用户 A：多 API 个人开发者

特征：

- 购买或申请了多个官方 API 与中转站 API；
- 会填写 Base URL、API Key 和模型名称；
- 不希望部署 Docker 或维护服务器；
- 经常忘记自己拥有哪些模型、端点和额度；
- 希望复制一段代码或配置后立即使用。

核心诉求：简单、快速、透明、无需记忆供应商差异。

### 3.2 核心用户 B：小型开发组织

特征：

- 多个项目共享若干 API 供应商；
- 重视稳定性、故障切换、预算、审计与可追溯性；
- 需要以统一端点降低业务代码与供应商的耦合；
- 目前不一定需要完整企业 IAM 或云控制台。

核心诉求：可靠、可观测、可配置、可迁移、可审查。

### 3.3 非目标用户

首版不以以下对象为主要目标：

- 需要多租户、SSO、组织成员权限和集中云管控的大型企业；
- 需要公网 SaaS API 网关的运维团队；
- 完全不理解 API 地址、密钥或模型概念的纯消费者；
- 需要支付、数据库事务、对象存储或云服务器管理统一编排的用户。

## 4. MVP 范围

### 4.1 首版必须提供

- Windows 10/11 安装与卸载；
- 托盘常驻和开机自启选项；
- 单机、单用户、多工作区；
- Provider YAML 注册与加载；
- OpenAI 官方 Provider；
- Anthropic Provider；
- Google Gemini Provider；
- 自定义 OpenAI-compatible Provider；
- API Key 安全保存与 Secret 引用；
- 安全能力探测和体检报告；
- 节点式工作流编排；
- OpenAI-compatible 本地统一出口；
- 主备切换、重试、超时、模型映射和简单条件路由；
- 流式响应透传；
- 运行状态、延迟、错误和基础用量审计；
- 聚合通知与故障恢复通知；
- Publisher 活文档与多语言代码模板；
- 工作区导入导出，且不包含明文密钥。

### 4.2 首版明确不做

- 公网发布；
- 团队账号、成员管理、SSO、RBAC 和云同步；
- 支付、数据库、对象存储和云服务器控制 API；
- 任意脚本节点；
- 任意循环、通用事件编程和完整低代码平台；
- 用户上传并执行不受信任代码；
- 自动执行具有资金、删除、购买或资源变更副作用的探测；
- Docker 作为普通用户的默认安装方式；
- 商业版、付费版或商业功能分层。

### 4.3 未来扩展但不构成首版承诺

- Anthropic Messages 原生出口；
- Gemini 原生出口；
- 局域网多人访问；
- 公网安全发布模块；
- 无头服务与 Docker 部署；
- 团队权限、集中策略和跨设备同步；
- 非 AI 类 API Adapter；
- 社区 Provider 仓库与签名分发；
- 自动生成 SDK。

## 5. 产品信息架构

### 5.1 应用总体布局

主窗口冻结为以下结构：

```text
┌──────────────────────────────────────────────────────────────┐
│ 标题栏                                                     │
├──────────────────────────────────────────────────────────────┤
│ 工具栏                                                     │
├──────────────┬─────────────────────────────┬─────────────────┤
│ 左侧栏       │ 中央主要工作区              │ 右侧属性/文档栏 │
│              │                             │                 │
│ 导航与资产   │ 画布、列表、仪表盘或向导    │ 当前对象上下文  │
├──────────────┴─────────────────────────────┴─────────────────┤
│ 底部运行信息栏：Runtime、Publisher、请求、错误、任务与日志 │
└──────────────────────────────────────────────────────────────┘
```

### 5.2 左侧栏

左侧栏承担稳定导航和工作区资产入口：

- 工作区切换；
- 概览；
- API 资产；
- 工作流；
- Publisher；
- 运行记录；
- 通知；
- 模板；
- 设置。

侧栏支持收起，但不应依赖仅图标表达复杂概念；收起时必须提供 Tooltip。

### 5.3 中央主要工作区

根据当前任务显示：

- OOBE 与任务向导；
- API 卡片与资产列表；
- 节点画布；
- Publisher 概览；
- 运行监控；
- 体检报告；
- 设置页面。

空白画布不是普通用户首次进入产品时的默认页面。

### 5.4 右侧栏

右侧栏是上下文面板，根据选中对象切换：

- 节点属性；
- Provider 配置；
- 密钥引用；
- 体检详情；
- 路由条件；
- Publisher 活文档；
- 代码示例；
- 错误解释与修复建议。

右侧栏应支持固定、调整宽度和关闭。

### 5.5 底部运行信息栏

底部栏不只是日志窗口，应提供分层信息：

- Runtime 状态；
- 已运行 Publisher 数量；
- 当前请求与后台探测任务；
- 最近错误；
- 可展开的结构化日志；
- 清晰区分业务请求、健康探测和系统事件。

默认保持紧凑，不持续抢占用户注意力。

## 6. OOBE 与渐进式复杂度

### 6.1 首次启动目标

用户首次启动后，应在不理解节点系统的情况下完成一次端到端成功调用。

### 6.2 OOBE 入口

```text
你想先做什么？

[管理我的 API]
添加并检查已有的供应商和密钥

[创建统一 AI 端点]
把多个模型发布为一个本地地址

[保证 API 不掉线]
配置主线路、备用线路和自动切换

[导入现有工作区]
打开已分享的工作区或模板
```

### 6.3 推荐首次流程

1. 选择 Provider 或自定义 OpenAI-compatible。
2. 填写 Base URL、API Key 和可选组织信息。
3. 将密钥安全写入凭据保险库。
4. 执行低成本、无副作用探测。
5. 展示体检报告和能力可信度。
6. 自动生成一个基础工作流。
7. 创建本地 Publisher。
8. 展示可复制代码并提供“测试调用”。
9. 成功后引导用户查看或编辑节点画布。

### 6.4 简洁视图与专业视图

产品提供同一工作区模型的两种投影：

- **简洁视图**：资产、健康状态、Publisher、接入代码和关键策略。
- **专业视图**：完整节点画布、条件、转换、路由、审计和探测策略。

两种视图不得产生两套配置。简洁视图做出的改变必须能在专业视图中解释，专业视图的复杂配置在简洁视图中必须以摘要和风险提示呈现。

## 7. Provider 与 Adapter 模型

### 7.1 设计目标

新增一个使用既有协议的供应商时，原则上只新增一个 Provider YAML；新增一种协议能力时，新增或扩展 Rust Adapter，不破坏既有 Provider 和工作流结构。

### 7.2 Provider YAML 职责

每家供应商使用独立 YAML 文件，声明：

- 唯一 ID、名称、官网与文档地址；
- 所属协议 Adapter；
- 默认 Base URL 与可编辑规则；
- 鉴权字段和 Secret 类型；
- 固定 Header、查询参数和组织字段；
- 模型发现端点；
- 能力发现策略；
- 无副作用健康检查；
- 错误映射补充规则；
- 余额或配额查询能力；
- UI 表单提示和帮助信息；
- Provider 配置版本。

YAML 不负责：

- 执行任意代码；
- 实现复杂协议签名；
- 解析任意脚本；
- 处理网络流；
- 保存用户密钥；
- 绕过 Runtime 安全策略。

### 7.3 Rust Adapter 职责

- 构造协议请求；
- 鉴权和特殊签名；
- 请求与响应转换；
- SSE 或其他流式协议处理；
- 工具调用、图像、文件等协议语义；
- 标准错误归一化；
- 超时、取消和背压；
- 能力探测执行器；
- 安全边界与敏感字段脱敏。

### 7.4 Provider YAML Schema 初稿

以下为说明性草案，实际实现时需转化为带版本的严格 Schema：

```yaml
schema_version: 1

provider:
  id: anthropic-official
  name: Anthropic
  category: ai-model
  homepage: https://www.anthropic.com/
  docs: https://docs.anthropic.com/

adapter:
  id: anthropic-messages
  min_version: 1

endpoint:
  default_base_url: https://api.anthropic.com
  editable: true
  allowed_schemes: [https]

authentication:
  type: header-secret
  fields:
    - id: api_key
      label: API Key
      secret: true
      required: true
      header: x-api-key

headers:
  - name: anthropic-version
    value: "2023-06-01"

discovery:
  models:
    strategy: adapter
  balance:
    strategy: unsupported

probes:
  - id: connectivity
    kind: metadata
    side_effect: none
    default_enabled: true
  - id: minimal-generation
    kind: billable-request
    side_effect: billable
    default_enabled: false

ui:
  setup_help: "创建密钥后粘贴到此处。密钥将保存在系统凭据保险库中。"
```

### 7.5 Provider 文件位置原则

全部项目源代码、内置配置、测试和资源均放在根目录 `src/` 下。建议实现阶段采用：

```text
src/
├─ apps/                  # Tauri/Next.js 桌面界面
├─ crates/                # Rust Control Plane 与 Runtime
├─ providers/             # 内置 Provider YAML
├─ schemas/               # Provider、工作区与节点 Schema
├─ templates/             # 活文档和工作区模板
├─ tests/                 # 跨模块测试
└─ assets/                # 应用资源
```

这是实现建议；允许在不改变“所有源代码均位于 `src/`”这一冻结决策的前提下细化。

## 8. 能力探测与体检报告

### 8.1 探测层级

系统按照以下层级建立能力清单：

1. Provider 静态声明；
2. 标准发现接口；
3. 无副作用安全探测；
4. 用户主动授权的可计费探测；
5. 用户手动声明。

系统不得通过破坏性请求自动“猜测”能力。

### 8.2 可信度标签

每项能力必须附带来源和可信度：

- **已验证**：通过成功的真实探测确认；
- **供应商声明**：来自 Provider 或官方元数据；
- **Adapter 推断**：根据协议与响应推断；
- **用户声明**：由用户填写，系统未验证；
- **未知**：暂时无法判断；
- **验证失败**：曾尝试验证但未成功。

### 8.3 体检维度

- 鉴权有效性；
- DNS、TLS 和网络可达性；
- 模型列表；
- 协议兼容性；
- 流式响应；
- 工具调用；
- 视觉输入；
- 结构化输出；
- 上下文信息及其来源；
- 延迟；
- 限流信息；
- 余额与配额（仅在 Provider 支持时）；
- 计费探测成本提示；
- 最近成功时间；
- 连续失败次数。

### 8.4 安全约束

- 默认仅运行无副作用、低成本探测；
- 可计费探测必须明确标记并由用户授权；
- Provider 不支持余额接口时应显示“不支持检测”，不得伪造估算值；
- 宣传的上下文长度与实测结果必须分开显示；
- 探测请求与真实业务请求在审计中必须可区分；
- 探测应受频率限制并允许暂停。

## 9. 节点式编排

### 9.1 首版节点类型

| 节点 | 职责 |
|---|---|
| Adapter | 连接真实供应商，处理鉴权、端点和原始协议 |
| Probe | 按周期、事件或手动触发健康与能力检测 |
| Transform | 转换请求、响应、参数、模型名称和兼容字段 |
| Router | 负载选择、主备切换、重试与降级 |
| Guard | 限流、预算、权限、数据与内容保护 |
| Publisher | 将工作流发布为本地统一 API |
| Group | 封装一组节点，只暴露稳定输入输出 |

### 9.2 首版路由能力

- 固定主线路；
- 有序备用线路；
- 请求超时；
- 有上限的重试；
- 模型名称映射；
- 根据错误类型切换；
- 根据健康状态切换；
- 简单条件路由；
- 切换事件通知；
- 手动暂停和恢复节点或 Publisher。

### 9.3 图模型原则

- 节点端口必须具有明确的数据或控制类型；
- 不兼容端口不可连接；
- 环路默认禁止；
- Group 的内部结构可折叠，外部只暴露声明的端口；
- UI 坐标与运行语义分开保存；
- 删除或禁用节点前显示影响范围；
- 画布必须能解释一条请求当前会走哪条路径。

### 9.4 故障传播模型

运行时不通过任意反向遍历画布决定切换，而采用标准事件和策略决策：

```text
请求结果
  → 标准化错误/指标事件
  → 更新端点健康状态
  → Policy/Router 重新决策
  → 切换线路或执行降级
  → 聚合通知与审计记录
```

首版标准错误至少包括：

```text
AUTH_FAILED
RATE_LIMITED
BALANCE_EXHAUSTED
MODEL_UNAVAILABLE
PROVIDER_TIMEOUT
NETWORK_UNREACHABLE
TLS_FAILED
INVALID_REQUEST
INVALID_RESPONSE
CONTENT_REJECTED
INTERNAL_RUNTIME_ERROR
```

### 9.5 暂缓能力

第一版不提供任意脚本节点、任意循环、用户代码执行、复杂事件语言和通用低代码自动化。未来引入时必须单独设计权限、沙箱、资源限制和供应链安全。

## 10. Publisher

### 10.1 定义

Publisher 是一个完整的本地 API 产品单元，而不只是监听端口的节点。它将工作流的能力、协议、路由、鉴权、文档和运行状态统一呈现。

### 10.2 首版发布能力

- 发布 OpenAI-compatible API；
- 用户可配置监听地址和端口；
- 默认监听 `127.0.0.1`；
- 首版禁止公网暴露；
- 局域网或非回环地址必须作为高级行为处理，并提供显著安全提示；
- 保留未来原生协议出口和公网发布模块的扩展接口；
- 支持运行、暂停、停止和自动恢复；
- 支持独立的本地访问令牌；
- 不向客户端暴露上游供应商密钥。

### 10.3 Publisher 面板

每个 Publisher 必须提供：

1. **运行状态**：地址、端口、运行时长、请求数、错误率、延迟和当前路由。
2. **能力目录**：接口、模型、上下文、流式、图像、文件、工具调用等。
3. **活文档**：根据当前工作流真实能力生成的接口说明。
4. **接入中心**：多语言代码、SDK 示例、环境变量和客户端配置。

### 10.4 生命周期

- 关闭主窗口不停止 Runtime；
- 托盘菜单可查看状态并显式停止服务；
- UI 崩溃或重载不应中断已发布请求；
- Runtime 重启后恢复此前启用且配置有效的 Publisher；
- 更新应用时应尽可能缩短服务中断，并明确提示不可避免的中断。

## 11. Capability Manifest 与活文档

### 11.1 统一能力模型

Adapter 探测、工作流计算、Publisher 文档和运行时校验必须共享一个版本化的 `Capability Manifest`，避免文档与实际能力脱节。

```text
Provider/Adapter 能力
        ↓
能力归一化
        ↓
工作流与路由计算
        ↓
Publisher Capability Manifest
        ├─ 运行时校验
        ├─ 活文档
        ├─ 代码模板
        ├─ OpenAPI 描述
        └─ 客户端配置
```

### 11.2 Manifest 示例

```yaml
schema_version: 1
publisher: unified-ai
base_url: http://127.0.0.1:6188/v1

protocols:
  - openai.chat_completions

capabilities:
  text_generation:
    streaming: true
    tools: true
    vision_input: true
    structured_output: partial

models:
  - public_name: smart
    source: routed
    health: available
```

### 11.3 活文档要求

- 文档与 Publisher 当前配置同步；
- 示例绑定真实 Base URL、鉴权方式和公开模型名称；
- 不将任何上游密钥写入示例；
- 区分流式和非流式调用；
- 仅展示当前 Manifest 声明支持的参数；
- 工作流变化导致能力减少时，立即在文档中体现；
- 标明能力来源与验证状态；
- 提供一键复制和本地测试；
- 复制内容应能够独立运行，必要占位符必须明确标识。

### 11.4 首批语言和生态模板

通用语言模板：

- cURL；
- Python；
- JavaScript / TypeScript；
- Go；
- Rust；
- Java；
- C#；
- C++。

生态模板：

- OpenAI Python SDK；
- OpenAI Node.js SDK；
- 常见 OpenAI-compatible 客户端配置；
- 环境变量配置片段。

模板必须由结构化参数绑定生成，不允许为每个 Provider 复制一份难以维护的静态代码。

## 12. 审计、可观测性与通知

### 12.1 默认审计范围

默认记录元数据，不记录请求或响应正文：

- 时间；
- Publisher；
- 请求协议与能力类型；
- 公开模型名称；
- 实际路由目标的内部引用；
- 状态码和标准错误；
- 首字节延迟与总耗时；
- 输入/输出 Token（供应商可提供时）；
- 缓存命中信息（供应商可提供时）；
- 重试与故障切换次数；
- 用户可配置的请求关联 ID。

### 12.2 内容审计

- 默认关闭；
- 必须由用户主动开启；
- 开启前明确提示隐私、磁盘和安全风险；
- 支持按工作区或 Publisher 配置；
- 提供保留期限和清除能力；
- 密钥、鉴权 Header 和已知敏感字段仍必须脱敏；
- 内容审计不应成为路由转发的同步阻塞点。

### 12.3 通知状态机

通知围绕状态变化生成，而非围绕每次失败生成：

```text
健康 → 波动 → 故障 → 已切换 → 恢复
```

同一故障在时间窗口内聚合为一条持续更新的通知。示例：

> 中转站 A 连续失败 3 次，已切换至官方线路。业务请求继续运行。

通知级别：

- 静默记录；
- 应用通知中心；
- Windows 系统通知；
- 需要人工处理。

### 12.4 防刷屏规则

- 相同对象、相同错误、相同状态合并；
- 状态未变化时只更新计数与最近时间；
- 恢复时生成一次恢复摘要；
- 认证失败、余额耗尽等需要人工处理的事件可以提升等级；
- 用户可按 Provider、Publisher 和错误类型设置静默策略。

## 13. 密钥与安全模型

### 13.1 冻结安全决策

- 使用 Windows 系统凭据保险库保护密钥或保护本地密钥保险库的主密钥；
- 工作区配置只保存 Secret 引用，不保存明文密钥；
- 导出工作区永不包含明文密钥；
- 日志默认不保存请求正文和响应正文；
- 内容审计必须由用户主动开启；
- 上游密钥永不透传给下游客户端；
- UI 不直接承担上游网络请求与密钥处理；
- 第一版禁止公网暴露 Publisher。

### 13.2 Secret 生命周期

```text
用户输入
  → 通过受控命令交给 Rust Control Plane
  → 写入系统凭据保险库/加密保险库
  → 工作区仅保存 secret://... 引用
  → Runtime 按最小权限按需读取
  → 日志和错误统一脱敏
```

### 13.3 配置导入

导入包含 Secret 引用但本机没有对应密钥的工作区时：

- 工作区可以打开；
- 相关节点标记为“缺少凭据”；
- Publisher 不得错误启动为健康状态；
- 用户可逐项绑定本机已有 Secret 或重新填写；
- 不允许从不可信 YAML 自动访问任意系统凭据。

### 13.4 Provider 供应链安全

- Provider YAML 必须通过严格 Schema 校验；
- 内置 Provider 随应用版本发布；
- 首版不自动下载和执行远程 Provider；
- YAML 不支持脚本、动态模块加载或任意文件读取；
- Provider 只能引用白名单 Adapter 和探测类型；
- 未来社区 Provider 必须另行设计签名、来源、权限和更新机制。

### 13.5 本地发布安全

- 默认仅绑定回环地址；
- Publisher 生成独立访问令牌；
- 可配置监听地址不代表允许任意公网绑定；
- 非回环绑定必须通过安全检查和确认；
- 日志不得记录完整 Authorization Header；
- 管理接口与业务发布接口使用不同权限边界。

## 14. UI 视觉与交互规范

### 14.1 设计系统基线

UI 冻结使用 `@openai/apps-sdk-ui` 作为组件、设计令牌和无障碍基础。其官方定位是轻量、可访问的 React 设计系统，提供 Tailwind 集成令牌、基于 Radix primitives 的组件、暗色模式和响应式能力。

实现基线：

- React 18 或 19；
- Tailwind CSS 4；
- `@openai/apps-sdk-ui`；
- 优先使用库提供的组件和语义令牌；
- 自定义桌面组件必须延续其交互、焦点与无障碍规范。

官方参考：

- [Apps SDK UI 文档](https://openai.github.io/apps-sdk-ui/?path=/docs/overview-introduction--docs&globals=theme:dark)
- [Apps SDK UI 官方仓库与安装说明](https://github.com/openai/apps-sdk-ui)

该组件库原本针对 ChatGPT Apps。API ARRAY 复用其设计系统能力，但不继承 ChatGPT 内嵌 Widget 的尺寸、宿主通信或布局限制。

### 14.2 桌面材质

视觉方向冻结为暗色、具有桌面背景穿透感的厚重亚克力/毛玻璃界面：

- Tauri 窗口允许透明背景；
- 在透明窗口之上叠加较暗、较厚的亚克力或毛玻璃材质；
- 主要内容区域必须维持足够不透明度与文字对比度；
- 边框、表面、阴影和层级使用设计令牌统一表达；
- 背景穿透是氛围层，不得降低数据可读性；
- 节点画布、代码块、日志和密钥输入区域应使用更稳定的不透明表面。

### 14.3 可访问性与降级

- 遵循 Windows“透明效果”偏好；
- 系统关闭透明效果或 GPU/驱动不适合时，自动降级为不透明暗色表面；
- 不以模糊或颜色作为唯一状态表达；
- 支持键盘导航和可见焦点；
- 文字和关键图标满足可读对比度；
- 动画遵循减少动态效果偏好；
- 密钥输入支持显示/隐藏，但默认隐藏；
- 错误信息必须可复制并给出下一步建议。

### 14.4 卡片与节点

- 卡片标题区展示类型、名称和健康状态；
- 核心指标保持可扫读，不在卡片中堆叠完整配置；
- 详细配置进入右侧栏；
- 输入输出端口具有类型、方向、颜色与文字提示；
- 选中、错误、暂停、降级和运行状态具有一致视觉语言；
- Group 折叠后显示内部健康摘要和当前生效路径。

### 14.5 代码块

- 显示语言、用途、复制和测试按钮；
- 密钥只使用 Publisher 的本地访问令牌或占位符；
- 自动换行不得破坏可复制内容；
- 错误配置在复制前给出提示；
- 切换语言不丢失当前接口、模型和流式选项。

## 15. 技术边界与部署形态

### 15.1 逻辑分层

```text
Tauri + Next.js/React UI
        ↓ 本地受控管理接口
Rust Control Plane
        ↓
Rust Runtime / Local Gateway
        ↓
上游 Provider API
```

### 15.2 UI 职责

- OOBE；
- 工作区导航；
- 节点画布；
- 配置编辑；
- 体检和监控展示；
- 活文档与模板展示；
- 向 Rust Control Plane 发起受控操作。

UI 不负责密钥长期保存、核心协议转换或业务请求转发。

### 15.3 Next.js 使用边界

Next.js 用于组织 React 前端，但桌面 UI 应能够静态构建并由 Tauri 承载。关键能力不得依赖独立 Next.js Server、Server Actions 或服务端渲染才能运行，以避免额外端口和生命周期耦合。

### 15.4 Rust Control Plane 职责

- 工作区和配置管理；
- Provider 加载与 Schema 校验；
- Secret 管理；
- 节点图校验与编译；
- Runtime 生命周期；
- 体检任务调度；
- 审计、通知和状态查询；
- 管理接口权限边界。

### 15.5 Rust Runtime 职责

- Publisher 监听；
- 请求解析与协议转换；
- Router/Guard/Transform 执行；
- 流式透传；
- 超时、重试和取消；
- 指标与异步审计事件；
- UI 不在线时继续运行。

### 15.6 未来部署兼容

Rust Core 应避免依赖 Tauri UI 才能工作，以便未来复用为：

- Windows 桌面常驻服务；
- 无头本地服务；
- Docker/服务器部署；
- 团队集中部署。

这些部署形态不是首版交付内容。

## 16. 工作区与文件结构原则

### 16.1 用户工作区逻辑结构

```text
workspace/
├─ workspace.yaml        # 工作区元数据与版本
├─ graph.yaml            # 节点、端口和运行连接
├─ ui.yaml               # 坐标、折叠、面板等纯 UI 状态
├─ publishers/           # Publisher 声明
├─ policies/             # 路由、重试、预算和保护策略
├─ templates/            # 工作区内复用节点组
└─ secret-refs.yaml      # Secret 引用，不含明文密钥
```

实际实现可以使用单文件包或数据库，但必须保持以上逻辑边界：运行语义、UI 状态和 Secret 分离。

### 16.2 版本化

- Provider、工作区、节点图和 Capability Manifest 均必须有 Schema 版本；
- 加载旧版本时执行显式迁移；
- 不可迁移时以只读方式打开并给出原因；
- 保存前保留可恢复副本；
- 导入导出结果应具有确定性，便于版本控制和传播。

### 16.3 项目仓库结构

根目录冻结为仅包含以下三个入口：

```text
APIArray/
├─ README.md
├─ docs/
└─ src/
```

所有源代码、内置 YAML、Schema、模板、资源和测试都必须位于 `src/`。根目录不散落源代码或工具配置；如未来构建工具强制要求根目录文件，应先形成并记录结构变更决策。

## 17. 非功能要求

### 17.1 可靠性

- UI 关闭或崩溃时，Runtime 已发布服务继续运行；
- Runtime 重启后恢复有效配置；
- 单个 Provider 或 Publisher 故障不拖垮其他 Publisher；
- 审计写入失败不应默认阻塞业务流量；
- 健康检查不应阻塞真实请求；
- 配置更新采用校验后切换，避免将无效图直接投入运行。

### 17.2 性能

- 支持 SSE 流式透传；
- 降低请求体和响应体的重复复制；
- UI 不参与数据面转发；
- 指标与审计异步处理；
- Runtime 不因打开复杂画布而降低转发性能；
- 首版性能基准在实现原型后冻结具体数值。

### 17.3 隐私

- 默认仅保存必要元数据；
- 默认不上传遥测；
- 若未来引入遥测，必须选择加入并公开字段说明；
- 一键清除审计、缓存和本地工作区；
- Secret 清除与普通配置删除使用不同确认级别。

### 17.4 可诊断性

- 每个请求拥有本地关联 ID；
- 标准错误保留脱敏后的上游错误摘要；
- 用户可以导出不含密钥和正文的诊断包；
- 路由切换能够解释触发条件和选择结果；
- 体检失败必须给出失败阶段，而非只显示“不可用”。

## 18. 关键用户流程验收

### 18.1 添加 API

给定一个有效的 OpenAI-compatible Base URL 和 API Key，用户可以在一次连续向导中：

- 保存密钥；
- 完成鉴权检查；
- 获取或填写模型；
- 查看能力与可信度；
- 不进入画布即可创建基础 Publisher。

### 18.2 创建统一端点

用户可以将至少两个 Provider 接入同一工作流，通过公开模型名映射到不同上游，并发布为一个 OpenAI-compatible 本地端点。

### 18.3 复制即运行

Publisher 活文档至少为 cURL、Python、JavaScript/TypeScript、Go、Rust、Java、C# 和 C++ 生成与当前端点一致的示例；在满足本地环境依赖后，复制示例可以成功发起请求。

### 18.4 故障切换

当主 Adapter 连续出现符合策略的超时或可用性错误时：

- Router 切换到备用 Adapter；
- 上层 Publisher 地址不变；
- 审计记录切换原因；
- 通知中心只产生一条聚合事件；
- 主线路恢复后按照策略处理，不发生无控制抖动。

### 18.5 安全导出

用户导出工作区后，导出内容中不存在：

- 上游 API Key；
- Publisher 完整访问令牌；
- Authorization Header；
- 默认关闭状态下的请求或响应正文。

导入另一台设备后，系统明确提示重新绑定 Secret。

## 19. MVP 发布门槛

第一版可被视为达到可发布状态，必须同时满足：

- Windows 10/11 安装、升级、卸载和托盘常驻流程可用；
- OpenAI、Anthropic、Gemini 和自定义 OpenAI-compatible Provider 可配置；
- 至少 OpenAI-compatible 统一出口稳定工作；
- Secret 不以明文进入工作区、日志或导出文件；
- 节点图支持冻结范围内的节点和策略；
- 流式与非流式请求均可工作；
- 主备故障切换可重复验证；
- Publisher 活文档与八类语言模板可生成；
- UI 符合三栏、底部运行栏、暗色亚克力和降级规范；
- 默认回环监听，公网发布被阻止；
- 配置迁移、崩溃恢复和诊断路径经过测试；
- MIT 许可证文件和第三方依赖许可清单在正式发布前齐备。

7. 上游余额、缓存命中和上下文信息的真实可探测比例。
8. Runtime 独立进程与同进程常驻方案在首版工程复杂度上的权衡。

这些假设应通过原型、遥测选择加入后的匿名指标或直接用户反馈验证，不得在验证前转化为夸大的产品承诺。

## 22. 冻结决策清单

以下决策自 2026-07-11 起冻结：

- 产品名称为 **API ARRAY**；
- 产品采用 MIT 开源许可，不规划商业功能分层；
- 首发支持 Windows 10/11；
- 产品为 Tauri 桌面应用，前端使用 Next.js/React，运行核心使用 Rust；
- 普通用户无需 Docker 即可安装和常驻运行；
- UI 采用左侧栏、中央主要工作区、右侧栏、顶部标题/工具栏和底部运行信息栏；
- UI 使用暗色厚重亚克力/毛玻璃方向，并提供不透明降级；
- `@openai/apps-sdk-ui` 是组件、令牌和无障碍基线；
- Provider 以每家供应商一个 YAML 的方式声明，协议能力由 Rust Adapter 实现；
- 首批 Provider 覆盖 OpenAI、Anthropic、Gemini 和自定义 OpenAI-compatible；
- 第一版统一出口为 OpenAI-compatible；
- 默认监听 `127.0.0.1`，地址可配置，但首版禁止公网暴露；
- 第一版为单机、单用户、多工作区；
- 第一版节点为 Adapter、Probe、Transform、Router、Guard、Publisher 和 Group；
- 第一版支持超时、重试、主备切换、模型映射和简单条件路由；
- 第一版不提供任意脚本、任意循环和通用事件编程；
- Secret 使用系统凭据能力保护，工作区只保存引用；
- 默认不记录请求和响应正文，内容审计需主动开启；
- 工作区导出永不包含明文密钥；
- Publisher 必须生成活文档；
- 首批通用模板包括 cURL、Python、JavaScript/TypeScript、Go、Rust、Java、C# 和 C++；
- 根目录只保留 `README.md`、`docs/` 和 `src/` 三个入口；
- 全部源代码、内置配置、资源和测试均放入 `src/`。
